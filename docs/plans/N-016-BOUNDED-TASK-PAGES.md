# N-016实施计划：有界任务查询与分页契约

本机原型已按此计划实现并验证，最终186项Swift、48项Node、8项管道及CLI通过；结果与限制见[验收范围](N-016-ACCEPTANCE.md)和[结构化证据](../evidence/n016-2026-10-15.json)。下文保留实施前的问题和设计范围。

当前durableJobs会读取当前受众的全部任务，overview再在内存统计，桥接只能用总响应预算拒绝过大结果。这不适合把当前原型视作大型NAS任务中心。下一步先让任务查询和统计有界，不启动浏览器或生产服务。

1. 为任务列表设计固定上限的页大小、明确SQL排序和不透明继续游标；游标绑定宿主会话、用户/应用受众、查询参数及寿命，不能选择数据库或跨用户继续。禁止将客户端任意SQL/排序表达式直接拼入查询。
2. 确定实时列表语义：任务状态可能在翻页间变化，新任务也可能插入；逐页读取不能冒充数据库一致性快照。采用稳定排序键前须验证比较、唯一性及边界，不假设展示语言排序等于数据库排序。
3. 用数据库聚合读取任务统计，避免overview加载所有任务；保留Schema 3、受众及只读模式校验。若确需Schema变化，必须进入版本迁移、快照、停写和恢复验证。
4. 版本化新增API/客户端DTO，不悄悄截断现有listJobs。旧接口如何过渡需明确；游标数量、寿命、响应预算及重放/撤销边界要有负测。
5. 使用多页合成任务验证无越权、页上限、边界/空页/重复/状态更新、游标过期与退出、只读恢复和不存在数据库不回退。受控样本测试不声称30TB或生产吞吐验证。
6. 核心变更后适当定向及未过滤全量回归，更新需求有限子项、ADR、证据、PROGRESS/NEXT_TASK，并按用户长期授权中文提交/推送开发分支。

事件已有数据库limit/ACK，但尚无通用浏览器订阅；大目录分页与稳定目录变化检测另行设计，不套用任务SQL游标。网页窗口仍等用户回家实测，不自动启动预览或修改设置。
