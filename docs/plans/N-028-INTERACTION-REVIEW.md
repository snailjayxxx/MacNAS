# N-028：回收与恢复交互、权限和生命周期审查

日期：2026-10-16，Asia/Tokyo。本文是设计审查及后续合成验收方案，没有新增运行接口、数据库表、文件效果或网页按钮。依据[N-028范围](N-028-RECYCLE-BIN-DESIGN.md)、[桌面契约](../contracts/DESKTOP_API.md)和[ADR-020](../decisions/ADR-020-bounded-file-copy.md)。当前网页仍只连接显式内存fixture；52项历史实际浏览器用例仍全部未执行，权限状态未变，本设计不启动浏览器。

## 三类标识与两条权限边界

回收、恢复均从单个常规文件、同设备、独立批准的新建合成目录开始。目录、批量、跨设备、覆盖、永久删除、系统垃圾桶、真实NAS及后台保留期清扫均不在本阶段实现范围。界面名称使用“移入回收站”和“恢复”，避免让“删除”同时指代回收与永久移除。

|标识/资料|用途|不能推导出的权限|
|---|---|---|
|短期预览ID|固定本次意图、当前授权及文件/父目录身份，明确确认一次|不是持久恢复凭据；退出、撤权、重批或重启后不能继续确认|
|持久操作ID|关联一次已确认动作及其协调记录、重读原结果，防止丢响应后误建新动作|不是文件访问令牌；原结果查询不授予再次移动、恢复、读取内容或取消能力|
|回收条目ID|定位一份受控回收记录及其不可复用的私有对象身份，供获准者发起新的恢复预览|不是宿主路径；看到条目、知道ID或持有导出包都不能打开其文件|

持久记录只保存逻辑资料库/相对原位置、主体、操作关联及身份核对材料；宿主根路径、描述符、会话凭据和批准能力不进入可携状态。原路径、大小、主体和回收时间都是受众受限的业务元数据，不能通过猜测ID泄露。原始文件名/路径按普通文字呈现，不作翻译键或HTML。

首版建议只允许当前管理员在开发模式、当前资料库有效readWrite绑定下操作，且回收与恢复分别需要宿主独立批准。原有读取、mkdir/rename、上传及复制批准均不能替代。恢复还须明确有权访问该回收条目及目标资料库/目录；同卷限制不等于批准跨资料库恢复，首版恢复目的地限定条目所属逻辑资料库，跨库必须另行设计。

原主体是审计关联，不是永久授权。首版条目/记录查询限定原主体及当前允许的元数据受众；“管理员”不能单凭角色或已知ID接管他人条目。读者、恢复/回退模式不能移动文件。恢复模式下可设计独立、受控的数据库记录只读查询，但该查询不打开、核对或恢复物理文件；不能把它包装为可继续的文件任务。

## 回收流程

1. 在当前已加载文件中选择一个常规文件。行数据只帮助选取意图，宿主仍重新授权并固定来源。先展示逻辑资料库、相对原路径、大小及“移入该资料库的私有回收站”；不显示宿主私有路径。尚未核实的数据标注未知，不用演示容量代替可用额度。
2. 预览固定当前主体/会话、角色/模式、实例与generation、数据库身份、卷/介质/挂载及盘点修订、内容reader、独立回收批准、源文件及源父目录标记、私有回收目录身份和策略修订。普通文件、单链接、同设备、容量/条目额度等由宿主判断。预览不移动文件、不自动创建可恢复条目；若有预留，必须有界且随取消/到期释放。
3. 确认面板明确显示“原位置将不再显示该文件；文件保留于回收站，需另行恢复”。保留期限只表示策略中的到期/保留规则，不声称本阶段会自动永久删除。确认只提交原预览ID和真正的布尔确认，不能同时替换路径、文件或主体。
4. 已确认后固定原操作ID。移动前后、持久记录推进与响应编码之间分别核对。只有协调记录和受控文件身份支持该结论时，才展示“已移入回收站”；原路径不存在或同名条目出现都不能单独作为成功证明。
5. 成功后分别重读匹配的原目录与回收列表。用户已切换目录、身份或窗口时，结果不写入新上下文；原结果仍可从受控记录入口查询。目录重读失败只显示“操作已记录，列表需要重读”，不把已经完成的移动改成失败。

选择、名称、来源身份或策略变化后必须新预览。旧预览失效时明确显示已过期/目标已变化，不能在确认动作中悄悄替换意图。若已确认动作仍未解决，原操作ID必须保留；禁止以一次新的回收意图替代它来“重试”。

## 恢复流程与冲突

恢复从有权看到的回收条目开始。展示原位置、原主体、回收时间、大小、记录状态，以及“当前文件可恢复性是否已重新核对”；持久记录中的旧成功不冒充本次物理检查。

默认恢复到原资料库/原父目录/原名称，先重新验证条目对应的私有对象、回收记录版本、原主体受众、目标父目录和独立恢复批准。默认目标不存在、父目录已删除或被替换、源回收对象变化、卷重挂载、批准重发，都不能沿用旧预览。父目录缺失时要求明确选择现有的有权目录；本阶段不顺带创建目录。

目标已占用时返回无提交能力的冲突预览，保留回收对象和原条目。用户可选择同库的其他有权目录或输入新名称，再取得一个全新预览并再次确认；不覆盖、不自动改名、不复用旧确认，也不把重命名当成冲突消失的证据。名称比较与不覆盖发布需遵循现有原生目录安全规则，不能只靠网页区分大小写或Unicode字符串比较。

只有当前恢复动作核对完成，界面才显示“已恢复到〔新位置〕”。原回收记录转为已恢复的审计状态，不表示立即清除历史；同一条目在恢复处理中拒绝第二个独立恢复动作。恢复丢响应后，原条目暂时看不见不能证明恢复成功，更不能据此新建第二次恢复。需要查询原操作ID并核对日志、回收对象及目标三者关系。

## 状态、取消与文案

下面定义的是对外必须区分的语义；最终DTO/状态枚举需在持久协调设计定稿后单独冻结，不能把表中建议名称当成已存在的API。

|可证明的情况|界面行为|取消含义|
|---|---|---|
|预览ready、尚未确认|显示原意图和独立确认；允许放弃|取消预览并释放能力/预留，没有文件移动|
|已确认，能证明效果尚未开始且协调器已阻止其继续|显示已取消，并说明没有移动|取消必须与提交/协调器互斥，不能只改网页状态|
|已确认，正在移动或效果结果尚未确定|显示处理中/正在核对；保留原操作ID|只能请求停止尚未执行的步骤；请求取消不等于取消成功|
|已证明移入/恢复且记录完成|显示具体完成位置及记录状态|取消不能撤销；反向动作必须取得新的独立预览和确认|
|发布后的校验、同步、记录推进或响应不明|显示“结果尚未确认，文件可能已移动”|禁止承诺回滚、自动重交或清理不明对象|
|日志/物理身份矛盾或不足|显示需核对/需处理；保留记录及对象|不因取消、超时、关闭窗口或保留期到达而删除对象|
|notVisible或记录暂不可查询|显示暂不可核对，不泄露他人资料|不证明没执行、不授予新确认或取消能力|

“取消中”“正在核对”不能显示完成勾选或成功提示。若宿主已移动，取消回复应保留已发生效果/未解决结果；不能只返回cancelled。泛化的failed也不能暗示原文件仍在原处：结果投影必须区分“已证明没有效果”“已证明有效果”和“尚不确定”，或提供等价的明确状态。网络中断、AbortSignal、窗口关闭及source.dispose本身都不能证明宿主取消成功。

## 撤权、丢响应和重启后的规则

- **撤权/重批**：已打开的描述符不替代当前批准。预览、确认、效果前后与结果投影分别校验相应权限。撤权前能够证明未移动时才可取消；已经移动或处于不确定窗口时保留协调记录与私有对象，进入等待重新批准/核对。新批准使用新epoch，旧预览绝不复活。允许独立的原主体清理入口释放尚未使用的预览资源，但不能借清理权限反向移动文件。
- **丢响应**：客户端固定原操作ID，不再自动确认、不更换幂等意图、不根据路径有无判断结果。存活连接可显式只读查询原结果。请求级ID仍一次性，若后续设计允许查询/核对重试，应换请求ID并保持原业务操作ID；文件动作是否能重放由持久协调器证明，网页不决定。
- **连接失效**：保留未解决引用和用户可理解的错误。不得自动重连、回退fixture或增加预算；身份所有者明确建立的新来源是新的能力上下文。新连接只可在当前元数据授权下读取原记录，不能把记录ID导入客户端写能力表。
- **宿主重启**：启动时可以读取、校验和展示数据库协调记录，将未解决条目标为需要当前批准；不能凭持久记录重新打开宿主目录、按旧绝对路径查找、重建旧句柄或重新移动。重启后的文件核对须先由宿主重新批准同一逻辑实例、数据库、卷/介质/挂载及内容目录，再验证旧记录与当前对象。generation/实例/数据库或卷身份不符时保持未解决，不在新位置自动接管。重新批准的只读核对不能推进阶段或配额；已有持久post的写终结另需下节独立settle批准。若确认需要新用户意图，应重新预览并明确确认，不复活旧previewID。
- **原结果与当前核对分开**：数据库记录查询可以显示“上次记录为已移入/已恢复”和上次核对时间；它不能悄悄扫描文件系统。当前物理可恢复性、外部效果核对的时间/结论以及当前缺少哪项批准应独立展示。只看到completed历史记录不保证当前文件仍存在或内容不变。导入、回退和独立候选数据库同样不自动取得旧文件访问权。

## 只读核对与写终结分开

`reconcileFileEffectObservation`是重新批准后的有界文件观察：只分类sourceOnly、candidateMoved、matchedPost或ambiguous，不改变数据库阶段、entry、配额或历史回执，不执行rename/unlink。读到matchedPost也不等于完成，普通状态查询更不能顺带触发文件核对。

`settleObservedFileEffect`是独立的写终结路径，须取得当前readWrite及单独settle批准，保持原operationID/意图并另记reconciler。仅当原记录已有持久post证据、当前双端匹配且来源/目标父目录可重新同步复查时，才可CAS补终结和按原方向转为retained/released；该路径从不rename/unlink。无持久post的candidateMoved保持未解决，不由新批准采纳、不补造post，也不以新ID再次移动。核对批准与settle批准都不复活旧preview/确认能力。

## 刷新、窗口与来源生命周期

窗口控制器继续借用共享来源；关闭窗口只释放自身预览/控制器，不关闭共享会话或客户端。source.dispose同步禁止新业务，尽力释放其真实拥有的短期预览/未提交能力；同ID在途调用结束后再清理，迟到预览返回后仍回收本地头及可取消的宿主能力。观察未知操作/条目状态不得登记所有权。仍使用有界本地记录和在途预留，不能用自动重连、额外来源或增加上限隐藏泄漏。

已确认的回收/恢复一旦交给持久协调器，不再等同于上传暂存或复制预览。窗口/source关闭可以丢弃本地UI和未提交能力，但不能删除协调记录、清除未解决操作、要求宿主撤销已移动文件或启动反向移动。关闭期间的迟到完成不得恢复旧窗口，也不得移除目标。身份所有者结束旧会话后，不向新身份回灌旧详情；原主体以后在新获准来源中查询原操作，仍须经过元数据受众校验。

“刷新”只重读当前位置/回收列表或显式查询原结果，不提交文件动作、不建立批准、不自动核对物理文件。刷新列表的临时失败保留有标记的旧内容，禁止把旧行作为新确认能力。文件浏览继续采用当前页/已加载范围和游标预算；回收列表也要独立分页，不一次加载所有持久记录。筛选、翻页和恢复目标选择都不能抹去未解决的原操作ID。
