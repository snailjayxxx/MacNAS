# N-028：单文件回收与恢复的文件系统审查

日期：2026-10-16。仅为设计审查；没有新增运行接口、迁移、真实回收目录、文件移动或清理行为，也没有执行新的文件系统故障测试。依据[N-028接续](N-028-RECYCLE-BIN-DESIGN.md)及现有`DescriptorLibrary`、`TransferDescriptors`、`FileOperations`代码。

范围与主设计及ADR-021对齐：明确批准的新建合成APFS目录、同设备、0至16MiB的单个常规单链接文件；恢复只到原逻辑资料库内有权目录。初始持久限额为64MiB reserved+retained、64个entry历史、256个operation历史及8个未终结操作。30天仅记录保留策略，到期仍保留并收费，不能把复制的内存预算当成持久配额。目录、跨库恢复、跨设备、永久删除、后台清扫、系统垃圾桶和正式NAS均不进入本阶段。

## 现有结构能复用什么

- `DescriptorLibrary`的逐级`openat`、`O_DIRECTORY/O_NOFOLLOW/O_CLOEXEC`、同设备检查、根与父目录重新核对，可作为路径访问基础。`DirectoryStamp`包含设备、inode、mode、links、size、mtime和ctime，适合本次打开期间的变更检查；不是跨重启身份凭据。
- `TransferDownload`展示了同时核对固定文件FD与原名称的做法。回收时须额外持有来源父目录、私有回收目录及文件FD；恢复时持有回收对象、回收父目录、批准的恢复父目录及文件FD。
- `RENAME_EXCL`可防止覆盖目标名称。它仍按来源父目录与名称操作，不是“仅当此名称仍指向已打开FD时才移动”的原子比较交换。检查与rename之间的替换竞态只能检测部分后果，不能承诺阻止敌对本机进程。
- `TransferStaging.publish`的发布后完整stamp基线可参考：rename允许预期的ctime变化，随后完整stamp必须保持一致，不能一直忽略ctime。已验证过的“同长度改写再恢复mtime”反例仍应保留。

不能直接复用`DescriptorLibrary.applyMutation`作为可恢复回收：它限定同父目录改名，只有内存回执，没有两个父目录的同步与持久效果协调。也不能用`TransferStaging`承载回收对象：其`deinit`会尝试unlink尚未发布的私有暂存，而回收对象、移动结果和身份不明对象都必须保留。应设计独立、析构只关闭FD的双目录移动原语。

## 目录、身份与批准

回收位置必须由宿主在批准的来源设备上选择，不能固定假设实例`host-binding`与所有资料库同设备。回收目录不向普通目录浏览暴露，不接受客户端根路径。每个对象使用随机且持久固定的私有对象键；恢复到用户目录时重新预览单分量名称和完整相对路径。不要预建占位目标文件，否则`RENAME_EXCL`会把自己的占位物也视为冲突。

0700私有目录需要核对当前UID、类型、设备及被固定的目录身份；已有同名目录不匹配即拒绝采用。0700本身不能排除同UID进程、继承ACL或已有写FD。当前方案只服务可信合成宿主，不能据此宣称生产ACL隔离。不要为了“私有”而擅自chmod原文件、改ACL或改所有者；这会另增元数据效果和ctime变化。

日志至少绑定实例/代次、操作ID、动作与原主体、逻辑资料库/原相对路径、受控对象键、设备所属卷身份、两端目录身份、来源大小/类型/链接数/内容摘要、移动前stamp及取得的移动后stamp。`dev_t`、inode和现有挂载会话ID不能直接跨重启或跨Mac采用；重新连接必须由宿主重新批准并核对卷与目录。可另研究可靠的出生时间或文件标识字段，但不得把额外stat字段宣称为不可伪造的身份。

回收批准、读取回收记录的可见范围、恢复批准分别建模；已有内容读取、上传、复制和mkdir/rename批准不推导这些权限。恢复既要有权读取原回收对象，又要有原逻辑资料库内目标目录的恢复写批准；不代他人恢复。旧主体记录用于审计，不代替当前授权；未知用户映射不能自动接管。撤权后保留协调记录；没有当前宿主路径批准时不open/stat旧路径，不能借恢复流程补做移动。对外可见性仍需当前授权，他人和不存在统一notVisible。

## 建议的持久状态机

回收与恢复分别使用新操作ID；恢复记录引用原回收对象并固定本次目标。不要把恢复当成回收操作的自动回滚。

| 阶段 | 已知情况 | 允许的下一步 |
| --- | --- | --- |
| `preview` | 临时固定意图与两端身份，没有移动 | 过期或关闭；确认后登记持久意图 |
| `prepared` | 意图与配额预留已持久化，尚未进入rename尝试区 | 取得串行执行权后取消，或持久标记`armed` |
| `armed` | 尝试区写入已确认，外部效果可能发生 | 本次执行rename，或在中断后只读核对；不能因日志未推进就重做 |
| `observed` | 完整移动后stamp、摘要与两端观察已持久化；尚未证明所有同步完成 | 继续本次同步与最终检查；中断后新批准核对，完整匹配才补同步/终结，不能重搬 |
| `completed`，效果为`trashed` / `restored` | 移动、身份与同步检查通过，效果回执已持久化 | 读取原回执；恢复须创建另一个明确确认的意图 |
| `cancelled` | 仅prepared，执行锁已阻止准入且能证明没有移动 | 回收释放预留；恢复entry继续retained；新意图重新预览确认 |
| `uncertain` | 效果、身份、同步或持久回执存在不确定性 | 保留对象、意图和配额；只有可信持久post证据与当前双端完整匹配时才可结算，否则只读观察 |

`uncertain`及其观察分类不是自动重试状态。预览过期不等于持久操作取消；已进入`armed`后的期限届满不得销毁意图或对象。容量不足时在移动前拒绝；不确定对象仍占保守预算，不能通过超时释放配额掩盖已有保留文件。

同一操作ID与完全相同的意图只读取既有阶段/回执；同ID不同意图拒绝。数据库租约还需配合本宿主对操作及对象的串行执行权。统一按实例门→vault执行锁→DB锁顺序取得，导出使用实例排他门，操作使用共享门；不得持有DB锁再等待宿主锁。租约到期不证明旧工作者已经停止；旧工作者可能继续完成rename，不能让新工作者仅凭租约过期再次执行。进程锁也不是跨Mac强fencing。

## 一次移动的建议顺序

1. 在固定来源FD上有界读取摘要，核对文件为常规文件、`nlink == 1`、大小与完整stamp不变；核对两端目录、当前批准、卷身份、目标无规范化冲突及设备一致。
2. 持久提交原意图、来源证据和完整配额预留；随后持久提交进入`armed`，确认写入后才允许rename。两次提交之间仍可安全拒绝，不能先rename再补第一份意图。提交回复不明时先核对原记录及执行权，不能先做文件效果。
3. 在串行执行权内复查来源FD、原名称、两端目录和批准，调用一次描述符相对的`renameatx_np(..., RENAME_EXCL)`。`EXDEV`或不支持该原语时拒绝，不退回普通rename、复制后unlink或自动创建父目录。
4. 系统调用成功后立即在内存标记“效果已发生”，取得移动后完整文件stamp；匹配原设备/inode/类型/链接数/大小/mtime，仅允许rename带来的预期ctime变化。核对新名称与FD一致、旧名称确实不存在，再核对授权与目录身份。旧名称若被别人重建，保留新旧对象并标记不确定，不删除重建物。
5. 将当前完整移动后stamp、摘要与两端观察持久写为`observed`，再将文件与两个父目录的同步结果分别记录；即使一次同步失败，也要保留已知的移动事实。同步后再次检查移动后完整stamp、内容摘要和两端身份。任何本次移动后的检查、授权、同步或期限失败均进入不确定状态，不反向rename。`observed`不是文件系统耐久性证明。
6. 最后提交效果回执与配额转换。数据库提交结果不明时查询原操作ID，不能重新执行文件效果。响应编码或传输失败不改写已有成功回执；客户端只读核对原ID。

fsync成功只能作为本原型成功条件之一，不能据此宣称已证明断电持久性。已有写FD仍可能继续修改被移动文件；打开只读FD或移动到私有目录不能把原内容变成快照。需要持续内容不变的保证时须另行设计并验证隔离措施。

## 崩溃后只读核对与自动恢复拒绝表

以下“匹配”必须包含当前宿主重新批准、正确卷/目录、常规单链接、受控名称、大小与摘要等证据，不能只看路径存在、inode相等或内容相同。

| 原位置 | 本次目标位置 | 处理 |
| --- | --- | --- |
| 原对象匹配 | 不存在 | prepared且新批准/独占锁/固定意图一致时可取消；armed或更后阶段不能据此证明从未移动，不能取消或自动重做原ID |
| 不存在 | 对象匹配 | observed/uncertain有可信持久post证据时，可在新核对批准下补同步/终结原意图；仅armed/pre证据或缺失post-stamp时不凭位置与摘要认领成功 |
| 任意对象存在 | 任意对象存在 | 保留两者，拒绝覆盖、unlink和“清理多余副本”；即使摘要相同也不证明对象归属 |
| 不存在 | 不存在 | 不证明取消；保留日志，标记丢失/不确定，不用其他同名文件补造结果 |
| 链接、特殊文件、陌生目录或身份失配 | 任意 | 拒绝采用；不跟随链接、不扫描全盘猜测对象、不删除陌生名称 |

还必须拒绝：持久日志缺失/损坏/来自另一实例或数据库；只有可携包而没有本机回收对象身份；挂载返回但旧批准失效；回收根被替换；恢复父目录缺失或已更换；恢复名称已存在（包括规范化碰撞）；出现额外硬链接；内容/mtime/ctime不符；设备改变；同步或数据库效果回执结果不明。保留期届满不是自动永久删除授权。

在`armed`后被SIGKILL、又没有持久移动后证据的窗口，首次设计应保守进入`uncertain`；目标看似匹配只可分类为`candidateMoved`。这意味着“可恢复”首先保证记录与对象被保留、可核对并可再次由用户明确选择操作；不等于所有崩溃窗口都能自动恢复完成。

只读observation仅分类；observed证据完整后的补同步/终结属于受新核对批准、宿主锁和原ID/revision CAS约束的结算路径，另记reconciler，不再rename/unlink。结算按原动作进行reserved→retained或retained→released，不能把它描述为不写状态/容量的纯只读查询。它不复活旧preview或旧写批准。

可另提议N-029执行审查研究“采纳已观察位置”：新宿主批准、新预览、新操作ID关联旧意图，重新打开当前FD，验证完整双端身份、持久移动后证据、摘要与同步，再记录当前核对结论。它不得调用rename/unlink、修改旧原主体或旧意图，也不能替`armed`补造不存在的历史postrename证据。旧位置出现陌生重建物、当前身份失配或记录不可信时继续保留并拒绝采纳。该提议尚未准入或实现，不是本阶段的自动恢复能力。

## 普通可携流程的阻断条件

新Schema4两表必须均空，且vault在明确宿主批准范围内被核对为空，普通export/upgrade/restore发布才可继续。released也属于非空历史；没有payload不意味着可以忽略日志。任何非空历史、retained、uncertain、孤儿或vault未知状态都阻断，不能只按“未终结操作数=0”放行，也不能由空DB推断vault为空。旧Schema1至3保持其原有检查，不假造不存在的新表。

导出停写不仅锁DB：先停止准入、取得实例排他门与vault执行锁、等待在途，最后冻结全部持久表。普通包没有vault，不能把单独pg_dump当成包含原文件的备份。候选出现任何回收记录后，DB恢复或Schema回退均不能让旧库重新成为可写文件执行者；保留两库与对象。专门payload备份、历史裁剪和跨Mac重绑另设计。

## 必须保留的反例与后续验证

- 最后一次来源检查后交换同名来源；rename可能移动替换物。结果必须不确定且所有对象保留，不能称为预先阻止了竞态。
- 已有写FD在移动后改内容；同长度改写再恢复mtime；增加硬链接；把回收目标或回收根替换成另一对象。只匹配设备/inode或忽略ctime不足够。
- rename已成功但在首次文件/目录同步前SIGKILL；同步成功但效果回执提交前SIGKILL；数据库提交成功但回复丢失。重放原ID均不能再产生移动。
- 来源与目标同时存在、同时缺失、相同摘要但不同inode、inode被复用、不同实例复制了日志。不得自动删除“多余”对象或认领未知对象。
- 恢复到原路径时已存在文件、目录、链接或规范化同名；原父目录被重建；撤权或卷重新挂载。必须重新预览有权目标，不能覆盖或按旧路径恢复。
- 取消与进入`armed`竞争、租约过期但旧工作者仍活着、结果查询和重试并发、容量预留提交后进程退出。取消必须有明确未移动的证据，未知效果仍占保守预算。

本文件仅提出故障矩阵。后续先做无文件效果的状态模型验证，再在单独授权的新建合成目录测试描述符、真实rename/fsync与进程中断。模型通过不能替代真实APFS、断电、跨Mac或浏览器验收；实现持久记录前仍须独立Schema4迁移与导出/恢复/回退设计。
